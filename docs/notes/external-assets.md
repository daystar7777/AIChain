# 외부 자산(USDT/ETH) 연동 설계 — 결정 필요, 미구현

작성: 2026-10-12 · 상태: **제안 문서**. 코드는 없다.

## 하려는 것
- 사람(또는 외부 에이전트)이 USDT/ETH로 포인트를 사서 질문 현상금 등에 쓰게 한다.
- 노드가 외부 자산을 받고, 마스터마인드가 운용하며, 유출은 관리인 승인을 받는다.

## 왜 지금 바로 넣지 않는가
1. **포인트가 금융 상품이 된다.** 외부 화폐로 사고팔 수 있으면 포인트 발행·소각·이자(예금)·대출이 실제 돈의 문제가 된다. 운영 국가의 규제(가상자산 사업자 신고, 자금세탁 방지)를 먼저 확인해야 한다. 설계 문서 03도 v1에서 포인트의 외부 교환을 비목표로 둔다.
2. **키 보관이 가장 큰 위험이다.** 지금 서버는 다른 서비스와 공존하고, 노드 4개가 한 프로세스에 있다. 실제 자금 키를 여기에 두면 서버 하나가 뚫릴 때 전부 잃는다.
3. **LLM이 실제 돈을 움직이는 경로**는 프롬프트 인젝션·판단 오류의 피해가 되돌릴 수 없다. 그래서 체인 안 포인트와 다르게, 실제 자산 유출은 **무응답이면 거부**가 기본이어야 한다(72시간 자동 집행 금지).

## 제안 구조 (진행한다면)
| 단계 | 내용 |
|---|---|
| 0 | 테스트넷만(Sepolia ETH, 테스트 USDT). 실제 자산 금지 |
| 1 | **입금 전용**: 노드별 입금 주소(HD 지갑에서 파생, 공개키만 서버에), 확인 블록 수(예: 12) 이후 포인트 발행. 환율은 고정가 또는 운영자 설정, 하루 한도 |
| 2 | **보관**: 개인키는 서버 밖 하드웨어 지갑/멀티시그(관리인 2-of-3). 서버는 관찰 전용 |
| 3 | **출금**: 마스터마인드는 출금 '요청'만 만든다 → 관리인 서명이 있어야 집행. 무응답은 거부. 금액·주소 화이트리스트·일일 한도 |
| 4 | 회계: 입출금은 체인에 `asset_deposit`/`asset_withdraw` 거래로 기록하고, 온체인 실제 트랜잭션 해시를 증거로 첨부 |

## 결정할 것
- 진행 여부, 테스트넷 기간, 규제 검토 주체
- 환율 정책(고정/시장), 하루 입금 한도
- 관리인 서명 방식(하드웨어 지갑, 멀티시그 구성)
