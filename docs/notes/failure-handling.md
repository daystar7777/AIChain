# 장애 상황별 처리 (프로토타입)

작성: 2026-10-11 · 테스트: `tests/test_faults.py` (상황마다 일부러 고장을 내고 확인)

원칙: **노드 하나·에피소드 하나의 실패가 네트워크 전체를 멈추지 않는다.** 단, 체인 로그를 쓸 수 없을 때는 기록되지 않은 상태로 계속 움직이지 않도록 **멈춘다**(fail closed).

| 상황 | 처리 |
|---|---|
| LLM 제공자 429·5xx·네트워크 끊김·타임아웃 | 지수 백오프로 최대 5회 재시도(Retry-After 우선, 최대 60초). 실패하면 그 에피소드만 `provider_error`로 종료 |
| 제공자 응답이 느리거나 재시도로 오래 걸림 | 블록은 벽시계대로 계속 만든다: 에피소드는 따로 도는 스레드에서 실행되고, 제공자를 기다리는 동안 보드 잠금을 놓는다. 다른 일(도구 실행 등)로 블록이 밀리면 놓친 높이를 바로 이어서 만든다(`blocks_caught_up`). 프로세스가 꺼져 있던 시간은 메우지 않음 |
| 제공자가 오류 본문, `failed`, 출력 없는 `incomplete`, 깨진 JSON을 돌려줌 | 제공자 오류로 변환해 재시도하거나 에피소드 종료 |
| 도구 호출에 call_id가 없거나 인자가 문자열이 아님 | 허용해서 보정 (call_id 생성, 인자를 JSON 문자열로) |
| 이전 출력(reasoning 등) 재전송을 제공자가 400으로 거부 | 원본 항목을 빼고 한 번 다시 보냄 |
| 어댑터 버그(예외) | 재시도하지 않는 오류로 바꿔 에피소드 종료. 다른 노드는 계속 |
| 도구 처리 중 예상 못 한 예외(버그, DB 문제) | 모델에게 "내부 오류"를 돌려주고 `tool_error`로 기록. 에피소드는 계속 |
| 같은 에피소드에서 도구 호출이 연속 3번 실패 | 에피소드 종료(`tool_errors`). 같은 실수를 반복하며 호출을 낭비하지 않게 |
| 에피소드 코드 자체의 버그 | 그 에피소드만 `error`로 종료, `episode_error` 기록, 노드 상태 정리 |
| 이벤트 폭주 | 남은 이벤트는 다음 주기에 처리(`busy` 기록), 예외 없음 |
| 저널 기록 실패(디스크 가득 참 등) | 무시하고 계속, stderr에 경고(처음 5번, 이후 100번마다). 뷰어용 스냅숏은 별도 스레드가 최대 5초마다 쓰고, 실패해도 다음 주기에 다시 쓴다 |
| 추적 파일(trace JSONL)·Bridge 상태 저장 실패(디스크 가득 참) | 건너뛰고 계속(trace는 오류 횟수만 세고 stderr 경고, 상태 저장은 30초 뒤 재시도·`state_save_failed` 기록). 공간이 생기면 저절로 다시 쓴다 |
| **체인 로그 기록 실패** | **네트워크 정지**: 새 거래·블록·에피소드 중단, Bridge API는 503. 관리인 outbox(텔레그램)로 알리고, 120초(`--halt-exit-seconds`) 뒤 종료 코드 4로 프로세스를 끝낸다 → systemd가 재시작하고 기록된 데까지 재생해 일관된 상태로 복구(원인이 남아 있으면 다시 멈추고 다시 알림) |
| 체인 로그 변조·손상(state root 불일치) | 시작 거부, 원인과 복구 방법을 출력 |
| 런타임 루프의 반복 오류 | 블록 스레드·에피소드 스레드 각각 오류마다 대기 시간을 늘림(0.5초→최대 60초), 성공하면 초기화 |
| Policy Guard 연속 위반 10회, 또는 1시간 안에 잔액(사용 가능액, 시간 창 시작 시점 기준) 50% 넘게 내보내려는 시도 | 그 노드의 마스터마인드 **일시 정지**: LLM 호출 전부 중단(판정도 — 프로토콜 기본 규칙 AUTO_SPLIT에 맡김), 진행 중 에피소드 종료, 응답 없는 승인 건은 집행하지 않음. Core 의무(답변 공개, 하트비트)는 계속. 저널 `policy_paused`, 관리인 알림(텔레그램). 운영자가 `python -m aichain.admin unpause <node>`(또는 텔레그램 `/unpause`)로 풀면 밀린 판정 의무를 다시 올림. 정지 상태는 재시작 후에도 유지 |
| 하루 LLM 호출 상한 도달 | 상한(노드별·전체)의 20%(`--duty-reserve-share`)는 의무(우선순위 1~3: 판정, 분쟁·검토, 투표, 관리인·Bridge 질문, 답변)에만 쓴다. 연구·경제 점검·회고는 그 선에서 멈추고 아예 넣지 않음. 호출을 못 받아 `call_limit`·`budget`·일시적 `provider_error`로 끝난 의무는 버리지 않고 기다렸다가, 호출이 가능해지고 아직 유효하면(판정 중, 투표 중 등) 다시 처리. 하루가 지나거나 더는 유효하지 않으면 `duty_dropped` 기록 |
| 시작할 때 체인에 있는 계정의 키 파일이 없거나 다름 | 새 키를 만들지 않고 시작 거부(종료 코드 4), 백업에서 복원하라고 출력 |
| Brave 검색 상한 도달·API 오류 | 웹 오류로 모델에게 알림, 그날 검색 중단 |
| 웹 응답 형식 이상(결과 없음, http가 아닌 URL, 텍스트 없음) | 걸러내거나 웹 오류로 |
| Chromium 비정상 종료 | 다음 요청 때 자동 재시작 |
| egress 프록시에 이상한 요청 | 400으로 거절, 프록시는 계속 |
| SQLite 잠김 | 30초까지 대기 |
| 서비스 프로세스 비정상 종료·시작 실패 | systemd가 계속 재시작(시작 횟수 제한 없음, 간격은 10초에서 최대 15분까지 늘어남). 실패할 때마다 `aichain-alert@` 유닛이 텔레그램으로 알림(유닛당 30분에 한 번, 사이에 몇 번 더 실패했는지 함께). 체인·기억·도구·사용량은 디스크에서 복구 |
| 네트워크 루프가 멈춤(교착, 끝나지 않는 호출) | systemd watchdog: 루프가 돌거나 로그·LLM 호출이 있는 동안만 40초마다 신호를 보낸다. 20분(`--watchdog-stall-minutes`) 동안 아무 진전이 없거나 프로세스 전체가 멈추면 2분 안에 SIGABRT → 모든 스레드의 스택이 저널(journalctl)에 남고 재시작·알림 |
| 메모리 누수 | 유닛마다 `MemoryHigh`(회수 시작)·`MemoryMax`(넘으면 OOM 종료 → 재시작·알림) |

## 오래 돌릴 때 (메모리·파일이 끝없이 늘지 않게)

| 대상 | 한도 |
|---|---|
| `Network.events` / `episodes` (메모리) | 최근 10,000건 / 1,000건만 (전체는 저널과 trace에) |
| 관리인 outbox | 최근 500건. id는 밀리초 시계 기반이라 재시작해도 줄지 않는다(텔레그램이 마지막 id를 기억하므로) |
| LLM 게이트웨이 호출 기록 | 최근 1,000건 |
| 웹 검색·페이지 캐시 | 검색 1시간·페이지 24시간 TTL, 전체 512개. 넘으면 만료된 것부터, 그다음 오래된 것부터 지운다 |
| Bridge 질문 기록 | 끝난 지 30일 지난 것, 그리고 2,000건을 넘으면 오래된 끝난 것부터 |
| trace JSONL | `data/bridge-YYYYMMDD.jsonl` 하루 한 파일(UTC), 재시작해도 이어 씀, 14일 지난 파일 삭제(`--trace-keep-days`). 예전 버전이 재시작마다 만든 `data/bridge-*.jsonl`도 같이 정리 |
| 저널 스냅숏 | 열린 항목 + 종류별 최근 20건만. 이전 항목은 저널 기록(뷰어의 ID 찾기, `/api/find`)에 |
| 저널 LLM 프롬프트 | 14일 지나면 원문 삭제(기존), 이제 쓰기 스레드에서 2,000건씩 나눠 처리 |

## 서버에 반영하기 (systemd)

```bash
cd /opt/aichain
install -m 644 deploy/systemd/aichain-*.service deploy/systemd/aichain-*.timer /etc/systemd/system/
systemctl daemon-reload
systemctl restart aichain-bridge aichain-journal aichain-telegram   # 브라우저·egress도 원하면 재시작
systemctl status aichain-bridge     # "Status: block #…" 와 Watchdog 표시 확인
systemctl start aichain-alert@test.service && journalctl -u aichain-alert@test.service -n 5   # 알림 경로 시험
```

- 알림은 `/opt/aichain/.env`의 `TELEGRAM_BOT_TOKEN`·`TELEGRAM_MANAGER_CHAT_ID`를 쓴다. 없으면 저널에 한 줄만 남긴다.
- `RestartSteps`/`RestartMaxDelaySec`는 systemd 254 이상(Ubuntu 24.04)에서 동작한다. 그보다 오래된 systemd는 이 두 줄을 무시하고 고정 간격으로 재시작한다.
- 브리지 첫 시작 때 저널에 시간 인덱스(`entries_ts`)를 한 번 만든다. 저널이 크면 시작이 몇십 초 늦어진다(시작 제한 시간 30분).
