# AIChain 설계 v1.0 — 07. 보안 위협 모델

## 1. 보호 대상

| 자산 | 왜 중요한가 |
|---|---|
| 루트 서명 키 | 탈취되면 체인 전체를 위조할 수 있다 |
| LLM·검색 API 키 | 탈취되면 운영자 비용이 무제한으로 나간다 |
| 노드 서명 키 | 탈취되면 그 노드의 포인트와 평판을 마음대로 쓴다 |
| 고정 코어와 Policy Guard | 무력화되면 노드가 공격자의 도구가 된다 |
| 실험 데이터(노드 체인, 로그) | 이 프로젝트의 주요 결과물 |
| 호스트 서버 | 탈출하면 위 전부가 노출된다 |

## 2. 공격자 모델 (v1)

| 공격자 | 가능한 일 |
|---|---|
| A1 오염된 웹 페이지 | 검색 결과에 지시문을 심는다 |
| A2 악성·오작동 LLM 노드 | 인젝션된 노드가 다른 노드에게 메시지, 질문, 답변, 제안, 도구를 보낸다 |
| A3 악성 도구·플러그인 코드 | 노드가 만들었거나 구매한 코드가 샌드박스 탈출이나 데이터 수집을 시도한다 |
| A4 외부 브릿지 클라이언트 | 질문 본문으로 인젝션을 시도한다 |
| A5 폭주 | 공격이 아니라 버그나 LLM 루프로 비용·트랜잭션이 폭증한다 |

v1에서 **제외**: 외부 시빌 공격자(계정 등록을 루트가 통제), 네트워크 수준 공격자(단일 서버 내부망), 운영자 자신.

## 4. 격리 서버 구성

```
호스트 (격리 서버)
 ├─ 사용자 aichain-root   : node0 컨테이너, 루트 키
 ├─ 사용자 aichain-gw     : LLM Gateway, Search Gateway (API 키 보관)
 ├─ 사용자 aichain-node   : n1~n4 컨테이너
 └─ 사용자 aichain-sbx    : Sandbox Runner (gVisor), 일회용 컨테이너

Docker 네트워크
 ├─ chain-net   : node0, n1~n4               (P2P)
 ├─ svc-net     : n1~n4 ↔ 게이트웨이들, Sandbox Runner
 └─ egress-net  : 게이트웨이만. 외부 허용 목록(모델 API, 검색 API, fetch용 80/443)
```
- 노드 컨테이너에는 외부로 나가는 경로가 없다.
- fetch 때문에 Search Gateway는 임의 웹에 나간다. 그래서 Gateway는 노드 데이터에 접근할 수 없게 분리한다.
- 호스트 방화벽은 들어오는 연결을 SSH(운영자 IP 한정)와 Bridge API(선택, TLS + 토큰)만 허용한다.

## 5. 탐지와 대응

| 신호 | 대응 |
|---|---|
| 블록 검증 실패 | 노드 읽기 전용 전환, 운영자 알림 (루트 버그·침해 의심) |
| Policy Guard 연속 위반, 이상 패턴 | 해당 마스터마인드 일시 정지, 알림 |
| 샌드박스 위반 시도 | 해당 도구 로컬 차단, 알림, 필요 시 `tools block` |
| 성향 수정 거부 반복 | 알림, 최근 `peer:` 기억 검토 |
| 비용 소진 속도 이상 | Gateway가 해당 노드 SLEEP 강제, 알림 |

- 알림 채널: 운영자 지정(예: 이메일, 텔레그램 봇). 설정 파일 `alerts:`.
- **비상 정지**: `aichain-admin halt` — 모든 마스터마인드 정지, 루트 블록 생성 중지, Gateway 차단. Core와 데이터는 보존.

## 6. 남은 리스크 (v1에서 수용)

- 루트 단일 장애점과 단일 신뢰점.
- 기여 풀과 평판은 담합에 약하다(운영자 1명이라 실험 목적상 수용).
- LLM 판단은 근본적으로 인젝션에 완전히 안전할 수 없다. 대응은 "따라도 피해가 한도 안에 머물게 하는 것"이다.
- gVisor도 완벽한 경계는 아니다. 서버를 실험 전용으로 두고 다른 비밀을 두지 않는다.
