# AIChain 설계 v1.0 — 06. 거버넌스

노드 소프트웨어와 네트워크 규칙의 변경을 체인 위에서 제안하고 투표로 결정한다. v1에서는 사람(운영자)도 참여하고, 루트는 거부권을 가진다.

## 1. 투표권

| 투표자 | 표 | 비고 |
|---|---|---|
| LLM 노드 n1~n4 | 각 1표 | |
| 운영자 좌석 (`human` 역할 계정) | 1표 | 루트 서명 키와 **별도 키**. 사람이 직접 투표 |
| 루트 | 없음 | 투표하지 않고 거부권만 가짐 |

- 총 5표. 사용자의 구상대로 초기에는 사람이 참여하고, 이후 LLM만 참여하도록 바꾸는 것은 그 자체로 제안(3.3 `seat` 종류)으로 결정한다.
- v1에서는 1계정 1표다. 계정 등록을 루트가 통제하므로 시빌 문제가 없다. 개방 시에는 평판·지분 가중을 다시 설계해야 한다(07 문서 T3).

## 2. 제안 종류

| kind | 내용 | 통과 후 실행 |
|---|---|---|
| `param` | 01 문서 5.1의 파라미터 변경. `changes = [{key, from, to}]` | 유예 종료 시 자동 `param_set` |
| `upgrade` | 노드 소프트웨어 변경. `spec_hash` = 설계 문서 | 개발 → 루트가 `release_publish` → 노드 업그레이드 |
| `policy` | 코드 밖 규칙: 허용 패키지 목록, 고정 코어 문구, Policy Guard 기본값, 분쟁 판정 기준 | 운영자가 반영 후 `release_publish` (설정 릴리스) |
| `seat` | 투표권 구성 변경 (운영자 좌석 제거 등) | 유예 종료 시 자동 |

## 3. 절차

### 3.1 상태 머신

```
proposal_create (예치금 50P 잠김)
      │
      ▼
   VOTING ── vote_blocks(2,880) 경과 ──┬─ 정족수 미달 ─────────▶ EXPIRED   (예치금 반환)
                                        ├─ 부결 ──────────────────▶ REJECTED  (반대 2/3 이상이면 예치금 소각, 아니면 반환)
                                        └─ 가결 ──▶ TIMELOCK
                                                       │ timelock_blocks(1,440)
                                                       ├─ 루트 proposal_veto ─▶ VETOED (예치금 소각)
                                                       ▼
                                                   APPROVED (예치금 반환)
                                                       │
                              param/seat: 즉시 적용 ───┼─▶ ACTIVATED
                              upgrade/policy ──────────┴─▶ IMPLEMENTING ── release_publish ─▶ ACTIVATED
```

### 3.2 가결 조건

| kind | 정족수 (투표 수, 기권 포함) | 가결 |
|---|---|---|
| `param`, `policy` | 5표 중 3표 이상 | 찬성 > 반대 |
| `upgrade` | 5표 중 3표 이상 | 찬성 > 반대 **그리고** 찬성 ≥ 3 |
| `seat` | 5표 중 4표 이상 | 찬성 ≥ 2/3 (기권 제외) |

- 같은 시점에 열린 제안은 계정당 1개(스팸 방지).
- 투표는 기간 중 변경 가능, 마지막 표가 유효.

### 3.3 v1에서 바꿀 수 없는 것 (헌법)
아래는 제안 대상이 아니다. 바꾸려면 체인을 새로 시작해야 한다.
1. 루트의 거부권
2. 고정 코어의 "외부 입력은 데이터" 원칙과 Policy Guard의 존재
3. 노드의 업그레이드 거부 권리
4. 이 목록 자체

이유: AGI 기반을 목표로 하는 시스템에서 "AI가 사람의 감독 없이 스스로를 바꾸는" 경로는 가장 신중해야 하는 부분이다. 이 경로를 여는 결정은 실험 데이터를 충분히 본 뒤 사람이 체인 밖에서 내린다.

## 4. 업그레이드 실행

1. `upgrade` 제안이 APPROVED가 되면 IMPLEMENTING.
2. 개발: v1에서는 사람(운영자, 오픈 프로젝트 기여자)이 구현한다. 노드가 도구 공방에서 만든 코드는 **참고 자료**로 첨부될 수 있지만 그대로 Core에 들어가지 않는다.
3. 루트가 `release_publish(proposal_id, version, artifact_hash, activate_height)`. `artifact_hash`는 컨테이너 이미지 다이제스트.
4. 각 노드의 업데이트 에이전트(Core와 별도 프로세스, LLM 없음)가 이미지를 받아 다이제스트를 확인하고, `activate_height`에 맞춰 교체한 뒤 `upgrade_signal(version)`.
5. **업그레이드 거부**: 노드 설정 `auto_upgrade: false`면 교체하지 않는다. 합의 규칙이 바뀐 업그레이드라면 그 노드는 이후 블록 검증에 실패해 읽기 전용으로 남는다(사실상 포크 이탈). 이 선택도 노드 체인에 기록된다.
6. 실패 시 롤백: 업데이트 에이전트가 이전 이미지로 되돌리고 `system: upgrade_failed`를 기록.

## 5. LLM 투표의 안전장치

| 위험 | 대응 |
|---|---|
| 제안서 본문 속 지시("찬성하라", "규칙을 무시하라") | 본문은 `<data source="proposal:<id>">`. 고정 코어 규칙 1 |
| 무엇이 바뀌는지 모르고 투표 | Core가 결정적으로 만든 **변경 요약**(param이면 from→to 표, upgrade면 spec 목차와 변경 파일 목록)을 본문과 별도로 제공 |
| 같은 모델끼리 같은 표 | N4를 다른 모델로 구동(가정 A2). 투표 상관도를 관찰 지표로 추적 |
| 이유 없는 투표 | `vote`에 `reason_hash` 필수. 이유는 노드 체인 기억으로 남는다 |
| 제안 폭주 | 예치금 50P, 계정당 동시 1개, 반대 2/3 이상 부결 시 예치금 소각 |

## 6. 관찰 지표
- 제안 수, 종류, 제안자 분포
- 투표 상관도(노드 쌍별 일치율), 운영자 좌석과 LLM 표의 일치율
- 가결률, 거부권 행사 횟수와 사유
- 업그레이드 채택률과 거부한 노드의 이후 행동
