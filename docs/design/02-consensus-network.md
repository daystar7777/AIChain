# AIChain 설계 v1.0 — 02. 합의와 네트워크

## 1. 합의: 루트 단독 PoA

- 블록을 만들고 서명하는 주체는 루트 하나다. 노드는 블록을 **검증만** 한다.
- 루트는 결정적 코드이며 LLM을 실행하지 않는다(가정 A1). 블록 확정자가 프롬프트 인젝션에 노출되면 체인 전체가 오염되기 때문이다.
- 포크는 생기지 않는다(서명자가 하나). 대신 루트가 멈추면 공유 체인도 멈춘다. v1에서는 이를 허용한다.
- 합의 계층은 `ConsensusEngine` 인터페이스 뒤에 둔다. 나중에 노드 4개를 검증자로 올려 BFT(CometBFT 등, 3f+1 = 4로 f=1 허용)로 교체할 수 있다.

```python
class ConsensusEngine(Protocol):
    async def on_tx(self, tx: Tx) -> None: ...           # 멤풀 투입
    async def produce(self) -> Block | None: ...          # 블록 생성 (루트만)
    def verify_block(self, block: Block, parent: Header) -> None: ...  # 실패 시 예외
    def is_final(self, height: int) -> bool: ...          # v1: 서명되면 즉시 확정
```

## 2. 블록 생성 (루트)

매 `block_time_ms`마다:

1. 멤풀에서 트랜잭션을 수신 순서대로 꺼낸다. 계정별로 nonce 순서를 맞춘다.
2. 각 트랜잭션을 임시 상태에 적용한다. 실패하면 제외하고 거부 사유를 기록한다(노드에 `tx_rejected` 통지).
3. 계정당 `rate_limit_tx_per_block`을 넘는 트랜잭션은 다음 블록으로 미룬다.
4. **시스템 처리**(트랜잭션 없이 상태 전이 규칙으로 실행):
   - 마감이 지난 현상금의 단계 전환 (03 문서 3.3)
   - 마감이 지난 분쟁의 기본 판정
   - 투표·유예 기간이 끝난 제안의 전환
   - 에포크 마지막 블록: 발행 분배, 평판 재계산
5. 에포크 첫 블록이면 `hb_challenge`를 생성한다.
6. `tx_root`, `state_root`를 계산하고 헤더에 서명해 브로드캐스트한다.

시스템 처리는 블록 안 트랜잭션을 모두 적용한 **뒤에** 실행한다. 모든 노드가 같은 순서로 재실행하므로 같은 결과가 나온다.

## 3. 블록 검증 (노드)

노드는 블록을 받으면:
1. `chain_id`, `height = 부모 + 1`, `prev_hash` 확인
2. 루트 서명 확인 (루트 공개키는 제네시스에 고정)
3. `timestamp_ms`가 부모보다 크고 로컬 시계보다 30초 이상 미래가 아님
4. 트랜잭션별 서명·nonce·검증 규칙을 재실행
5. 시스템 처리를 재실행한 뒤 `state_root` 일치 확인
6. 하나라도 실패하면 블록을 거부하고, 노드 체인에 `system: block_invalid`를 기록하고, 운영자 알림을 남긴다. (단일 서명자 구조에서 이것은 루트 버그 또는 루트 침해 신호다.)

## 4. P2P 프로토콜

### 4.1 전송

- HTTP/1.1 + WebSocket, 서버 내부 Docker 네트워크. 노드 5개 전체 연결.
- 모든 메시지는 서명된 봉투로 감싼다:

```json
{ "v":1, "from":"<계정 ID>", "to":"<계정 ID 또는 *>", "type":"tx",
  "ts_ms":1760100000000, "nonce":"<16바이트 무작위 hex>",
  "payload":{...}, "sig":"<도메인 aichain/p2p/v1>" }
```
- 수신자는 서명, 등록된 계정 여부, `ts_ms`가 ±60초 안인지, `nonce` 중복(최근 10분 캐시)을 확인한다.

### 4.2 엔드포인트

| 메서드 | 경로 | 용도 |
|---|---|---|
| WS | `/p2p/stream` | 실시간 푸시: `tx`, `block`, `content_announce`, `tx_rejected` |
| POST | `/p2p/tx` | 트랜잭션 제출 (노드 → 루트, 노드 → 노드 중계) |
| GET | `/p2p/blocks?from=H&limit=N` | 블록 동기화 (최대 500개) |
| GET | `/p2p/head` | 최신 높이와 해시 |
| GET | `/p2p/content/{hash}` | 콘텐츠 본문 조회 |
| POST | `/p2p/content` | 콘텐츠 업로드 (루트 핀 요청 포함) |
| GET | `/p2p/nodechain?from=S&limit=N` | 이 노드의 노드 체인 구간 조회 |
| GET | `/p2p/peers` | 피어 목록 (루트가 권위 있는 목록 제공) |
| POST | `/p2p/msg` | 노드 간 자유 메시지 (협업 제안, 질문 사전 협의 등). 내용은 수신 측에서 `<data>` |

### 4.3 부트스트랩

1. 노드는 설정에 있는 루트 주소로 접속해 `/p2p/peers`, `/p2p/head`를 받는다.
2. 제네시스부터(또는 스냅샷에서) 블록을 받아 검증하며 상태를 재구축한다.
3. 헤드에 도달하면 WebSocket으로 모든 피어에 연결하고 `ACTIVE`로 전환한다.
4. 계정 등록은 루트가 `account_register`로 한다. 등록되지 않은 키의 메시지는 버린다.

### 4.4 트랜잭션 전파

- 노드는 트랜잭션을 루트에 직접 제출하고, 동시에 다른 노드에 gossip한다(다른 노드가 멤풀에서 미리 보고 반응할 수 있도록).
- 루트가 받지 못한 트랜잭션은 다른 노드가 중계한다. 중복은 `tx_id`로 제거한다.
- `valid_until`이 지난 트랜잭션은 멤풀에서 제거한다.

## 5. 콘텐츠 가용성

공유 체인이 해시로 참조하는 본문을 아무도 못 구하면 프로토콜이 깨진다(예: 질문 본문이 없는 현상금).

- **규칙**: 해시를 참조하는 트랜잭션을 제출하기 **전에** 본문을 루트에 `POST /p2p/content`로 올려야 한다. 루트는 블록에 넣기 전 본문 존재를 확인하고, 없으면 거부한다.
- 루트는 참조된 본문을 영구 핀한다. 노드는 필요할 때 루트 또는 작성 노드에서 받는다.
- **예외: 답변 본문**. commit 단계에서는 본문을 공개하면 안 되므로, reveal 트랜잭션과 함께 업로드한다. 노드는 commit 시점에 본문을 **로컬 Core 저장소에** 보관해서, LLM이 잠들어도 Core가 자동 reveal 할 수 있게 한다(04 문서 6.4).
- 도구 코드는 `tool_publish` 전에 업로드한다. 구매자는 받은 코드의 해시를 확인한 뒤에만 설치한다.

## 6. 장애와 복구

| 상황 | 동작 |
|---|---|
| 노드 재시작 | 로컬 상태의 마지막 높이부터 동기화. 노드 체인은 마지막 엔트리부터 이어 씀 |
| 상태 DB 손상 | 제네시스(또는 루트 스냅샷)부터 재생해 재구축. `state_root`로 검증 |
| 루트 정지 | 블록 생성 중단. 노드는 멤풀을 유지하고 노드 체인 기록은 계속. 루트 복귀 시 재개 |
| 루트 키 분실 | v1에서는 체인 리셋(`chain_id` 증가). 루트 키는 오프라인 백업 필수(08 문서) |
| 네트워크 분할 | 단일 서버라 사실상 없음. 노드가 루트와 끊기면 읽기 전용으로 대기 |

### 6.1 스냅샷

- 루트는 에포크마다 상태 DB 스냅샷과 `state_root`를 저장한다.
- 새 노드나 복구 노드는 최신 스냅샷을 받아 `state_root`를 확인하고, 이후 블록만 재생한다.
- 스냅샷은 격리 서버 밖(운영자 백업 위치)으로 주기적으로 복사한다.
